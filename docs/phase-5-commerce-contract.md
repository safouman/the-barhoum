# Phase 5 Commerce and Entitlements

Planning baseline is `feat/course-platform` at `312355e`. Launch supports one-time base course purchases and optional standalone premium module upgrades, with one active offer per target. Base ownership covers current and future regular lessons. Premium access requires both its own grant and an active base grant. Purchases require a verified student session. Free previews remain accessible to visitors.

## Data and ownership

| Record | Contract |
| --- | --- |
| Offer | Stable ID, course ID, optional premium module ID, enabled state and current Stripe Price ID. Unique base offer per course and upgrade offer per module. Validate module ownership and classification. Manage offers through standard Payload Admin. |
| Order | Stable attempt ID, student ID, offer and target snapshot, Stripe account/mode and Price ID, amount in minor units, currency, tax/total as applicable, payment and fulfillment state. Unique Stripe Checkout Session and PaymentIntent references per account/mode. One open attempt per student and target via a partial unique index. |
| Payment event | Unique provider event identity per account/mode. Store type, normalized outcome, processing time and order association. Keep provider refund/dispute references and amounts needed for reconciliation. |
| Grant | Student, stable target and source order, state and reason, timestamps. One grant per source order, and at most one active grant per student and target. Serialize transitions by student and target. Premium dependency is evaluated on access and does not erase the premium grant. |

Use Stripe one-time Prices as the amount and currency source. Assign a new Price for a price change. Historical orders keep their snapshots. Offer disablement or removal from sale leaves existing grants intact. No order or grant mutation through generic Payload REST. Keep financial references when retiring an offer or content. Prevent deletion of financially referenced entities and block routine unpublishing of purchased content, published classification changes for a sold module, and placement changes that cross the paid boundary for sold curriculum. Exceptional retirement or access policy changes require separate approval. Ordinary editing, reordering, and adding regular lessons remain supported.

## Checkout and fulfillment

- Keep the one-to-one Stripe flow and existing webhook behavior. Remove logging of the Stripe key prefix in the existing client. Course commerce gets separate server-only configuration, a distinct webhook route and signing secret, a course marker and order ID on both Checkout Session metadata and PaymentIntent metadata, and a separate feature flag. If the legacy destination receives course events from a shared Stripe account, filter the explicitly marked course events after signature verification and before legacy side effects. Unmarked training traffic follows its existing path. Test both directions of isolation.
- `POST /api/course-commerce/checkout` takes `{ offerId }` and returns `{ orderId, checkoutUrl }` or a stable error code. Require a verified student and same-origin mutation. Revalidate available offer, authoritative Price, ownership, and the base prerequisite for upgrades. Neither browser amount nor Stripe identifiers are accepted as checkout inputs. Use one card-only Checkout Session in payment mode per order. Disable unapproved discounts, adjustable quantity and currency conversion so the displayed and charged pricing contract is testable.
- Phase 7 mandatory pre-launch gate: enforce detected Tunisian IP purchase eligibility server-side at Checkout creation and display Coming soon for affected visitors while preserving free previews. Phase 5 has no geographic gate or messaging. Test Mode Checkout is available from Tunisia.
- Reserve one attempt in Neon before calling Stripe. Use its ID for a stable provider idempotency key and recover ambiguous creates using the same attempt and parameters. Reuse open sessions. Confirm Stripe expiry or terminal state before creating a replacement. Recheck eligibility on every creation request. Keep external API calls outside the reservation transaction. If a redundant payment settles, retain the order, grant access once, and flag the extra payment for an operator refund.
- `POST /api/course-commerce/webhook` verifies the raw Stripe signature and accepted mode and routes only course orders. Retrieve canonical Stripe state, reconcile under per-order serialization, and guard against stale state overwriting newer decisions. Validate Checkout association, amount, currency, line item, quantity and paid state. In one transaction record the event, transition the order and write or update the grant. Acknowledge successful processing after commit. Return retryable failure for transient failures. Apply the same idempotent reconciler from an authorized refresh and an operator replay or reconciliation command.
- `GET /api/course-commerce/orders/[orderId]` returns only the signed-in owner's order state. `POST /api/course-commerce/orders/[orderId]/refresh` uses the same ownership check and bounded reconciliation. Return states include processing, fulfilled, failed, expired, and support required. A Stripe return URL is a status entry point. Webhooks fulfill even when a student closes the browser. Failure, abandonment and unpaid events never grant access.
- Successful full refund revokes the affected source grant. An open dispute suspends access. Restore after a win if the source payment still qualifies and revoke after a loss. Record partial refunds while preserving access by default pending an explicit policy change. Base refund or suspension masks premium access. A new qualifying base purchase restores access to previously purchased and otherwise valid premium modules. A paid premium upgrade can be recorded if base ownership lapses after valid checkout creation, and remains inaccessible until base access is restored.

## Access and purchase experience

- One server-only access resolver consumes stable student ID, published course ID, lesson ID and authoritative module placement/classification. Return explicit free, owned, or locked access. Resolve from published records. Avoid delivering protected video or file references in the course catalog, locked pages, prefetches or CMS responses. Use the same access decision for lesson content and exact attached file delivery.
- Retain Vimeo. Agent B tests the supplied video with the account's available embed privacy controls, the stable Preview hostname, and off-domain embedding. Use Embed only or Hide from Vimeo, domain restrictions and disabled downloads where available for paid assets. Confirm unauthorized app requests never receive the embed identifier or privacy hash. Domain restrictions control embedding, while Barhoum controls student authorization before serialization. Escalate if the actual plan or test asset cannot support the agreed MVP protection. Provider changes require separate approval.
- Reuse the existing private Blob stream. Authorize the exact published attachment on every request and return protected downloads with private, no-store caching. Keep authorized public/free downloads and administrator uploads working. Inventory paid resource references before enabling paid lessons. Move public paid copies to private storage and remove controlled public originals after verifying replacement. Reject paid external links that bypass access control and prevent exposing the same protected asset from a free lesson.
- Course detail shows the actual price, included content and one primary action. Student-specific state is resolved server-side and excluded from shared caches. Auth resumes a safe internal course destination, retaining purchase intent through password login, Google and email verification. An anonymous visitor can browse and play free content. Existing owners see Continue Learning. Eligible owners can buy offered premium modules. My Learning reads active base ownership and shows Browse Courses when empty. Make Courses, Login/Register, My Learning and Account discoverable using existing navigation styles. Use Stripe receipts and the existing support contact path.

## Shared implementation interface

- Payload slug `course-offers`, with fields `course` (required relationship), `module` (nullable relationship), `enabled` (default false), `stripePriceId` (required). Read and writes through CMS are administrator-only. Public offers are projected explicitly. PostgreSQL table `course_offers` uses `course_id`, `module_id`, `enabled` and `stripe_price_id`.
- PostgreSQL table `course_orders` uses `id` UUID, `student_id`, `offer_id`, `course_id`, nullable `module_id`, `stripe_account`, `livemode`, `stripe_price_id`, `amount_minor`, `currency`, nullable `tax_minor` and `total_minor`, nullable `stripe_session_id`, `stripe_payment_intent_id`, `checkout_url`, `expires_at`, `status`, `reason`, `created_at`, `updated_at`. Status is creating, open, processing, fulfilled, failed, expired, or support_required. Open-attempt uniqueness covers creating, open and processing.
- PostgreSQL table `course_payment_events` uses `stripe_account`, `livemode`, `stripe_event_id`, `event_type`, `order_id`, `outcome`, nullable `provider_reference` and `amount_minor`, and `processed_at`. Account, mode and event ID form the key.
- PostgreSQL table `course_entitlements` uses `id` generated integer, `student_id`, `course_id`, nullable `module_id`, unique `source_order_id`, `status` (active, suspended, revoked), `reason`, `created_at`, `updated_at`. Null module means base access. Active uniqueness applies separately to base and upgrade targets.
- Checkout, order status, refresh and webhook use the routes above. JSON errors use `{ error: { code, message } }`. Stable codes include UNAUTHENTICATED, INVALID_INPUT, NOT_FOUND, OFFER_UNAVAILABLE, ALREADY_OWNED, BASE_REQUIRED, and UNAVAILABLE. Status and refresh return `{ orderId, status, courseSlug }`. Stripe returns to `/checkout/return?orderId=...` and cancels back to the course. Use a configured trusted origin.
- Agent A supplies server-only `listCourseOffers(courseId)` in `lib/commerce/course-payments/offers.ts`. Return enabled, available offers with `{ id: number, moduleId: number | null, amountMinor: number, currency: string }`. Agent B supplies `getCourseOwnership(studentId, courseId)` and `listOwnedCourseIds(studentId)` in `lib/learning/entitlements/index.ts`. Ownership result is `{ base: boolean, moduleIds: number[] }` where module IDs represent effective access.
- Agent C builds presentation against those shapes with local fixtures. Coordinate final imports with the coordinator, who will connect the shared server view model to the pages. Agent B should allow an optional authenticated student ID in learning readers while preserving anonymous behavior. The coordinator will wire the verified session into shared page entry points as needed.
- Escalate schema or interface changes before relying on them. Each agent uses disposable databases and provider fixtures. Stripe Test Mode and protected Vimeo account checks run during coordinated integration.
